# Synthetic extractor test fixtures

**These fixtures contain no real game content.** Every identifier, god
name, trait name, and comment is invented (e.g. `Cindra`, `Verdan`, `Orithia`,
`Sable`, `Auric`, `Fennick`; `Ember`/`Root`/`Aether` elements;
`CindraStrikeBoon`-style trait ids). No real Hades or Hades II trait id,
god name, display string, or line of Lua has been copied into these files.
Copyright-wise, they're safe for public repos (unlike anything sourced directly
from the shipped games (I think??)).

**What they test, and what they don't:** these fixtures exercise
**extractor/parser logic**, i.e. can your code correctly walk `InheritFrom`
chains, recognize a symmetric `HasNone` clique vs. an asymmetric one,
distinguish a trait-vs-trait negation from a room-flag/reward-type gate,
synthesize a stable set identity for content that has no name in the
source, etc. This is done using hand-picked minimal input specifically shaped to
hit each piece of grammar. **They don't test grammar drift**, i.e. whether
the *real* games' data still matches the idioms these fixtures assume.
That's a different, ongoing risk (technically, Supergiant could rename a field,
add a new idiom, restructure a file, etc) and is covered by re-running the
extractor against the real game install and diffing against the last known-good
extraction (`../reference/hades1/`, `../reference/hades2/`, which are
gitignored), so not by these fixtures. Passing these fixtures proves the code
handles the shapes correctly, but says literally nothing about whether the
current game data still uses those shapes.

## `expected.json` is a target; `golden/` is the assertion

Two different things live beside each other here:

- **`golden/*.json`** is a **snapshot of what the normalizers emit today**,
  regenerated by `tests/regenerate_golden.py` and asserted byte-for-byte by
  `tests/test_golden.py`. It's a regression net. It doesn't claim that the
  output is *right*, only that it hasn't changed by accident.
- **`expected.json`** is the **schema this fixture set was written to
  specify**. Most of the gap has closed: `tier`, `blockedBy` and `activation`
  are all emitted now, and `elementCost` no longer is. What remains is that its
  `tier` is a category string (`Core`/`Legendary`/`Duo`/`Infusion`/`Cameo`)
  where the app's `tier` is a number (the ladder depth of a boon within its own
  god) — two unrelated concepts sharing one name — and its base-template
  exclusion rule, described at the bottom of this file, which the Hades I
  normalizer still does not apply. Treat what is left as a todo list, not as
  something a test should pass.

`raw/*.json` is the synthetic Lua dump the golden test starts from, produced by
running the real dumpers over `input/` with `EXTRACT_RAW` and
`EXTRACT_SCRIPTS_*` pointed here. It's committed so the test doesn't need a Lua
interpreter, which is what lets it run in CI.

Where the golden output already differs from `expected.json`, the difference is
a finding about the tool instead of about the fixture: `h1-shape` keeps three
base templates and a `DebugOnly` trait that `expected.json` excludes, and
`h2-shape` keeps a `DebugOnly` boon.

## Layout

```
fixtures/
  h2-shape/
    input/
      TraitData.lua           base templates + LinkedTraitData + TraitRequirements
      TraitData_Cindra.lua    one god's boons
      TraitData_Verdan.lua    a second god (ADDED, see below)
      TraitData_Duo.lua       a cross-god duo
      TraitData_Elementals.lua an infusion boon
      TraitData_Orithia.lua   a narrative-cameo "god" (ADDED, see below)
    expected.json
  h1-shape/
    input/
      LootData.lua            <God>Upgrade.LinkedUpgrades, prereqs INLINE, repeated
      TraitData.lua           flat trait table + scattered special-case fields
    expected.json
  README.md                   this file
```

**Additions beyond the originally specified file list:** `TraitData_Verdan.lua`
and `TraitData_Orithia.lua` were added to `h2-shape/`. The requested list
covered one god (`Cindra`) plus duo/infusion files, but several coverage
items need a *second* real, resolvable god to point at — a cross-god duo
needs two gods; an asymmetric negation needs a real (not dangling) target
on the other side; the narrative-cameo case needs its own concrete
boon. Both additions are minimal (3 boons, 1 boon respectively) and follow
the same per-god-file convention as `TraitData_Cindra.lua`.

## How the expected outputs were produced

Instead of being simulated by hand, each fixture was actually loaded through the
same Lua 5.5 + `engine_stub.lua` + `json_encode.lua` harness used for the real
extraction (see `../lua/`, `../normalize_h1.py`, `../normalize_h2.py`), and
`expected.json` was built by inspecting that real dump (`InheritFrom`
resolution, `GameStateRequirements` shape, etc) instead of by predicting what
Lua "should" produce. To reproduce:

```bash
lua -e '
dofile("../../lua/engine_stub.lua")
dofile("../../lua/json_encode.lua")
loadfile_stripbom("input/TraitData.lua")()
dofile_stripbom("input/TraitData_Cindra.lua")
dofile_stripbom("input/TraitData_Verdan.lua")
dofile_stripbom("input/TraitData_Duo.lua")
dofile_stripbom("input/TraitData_Elementals.lua")
dofile_stripbom("input/TraitData_Orithia.lua")
print(json_encode_object({ TraitData = TraitData, LinkedTraitData = LinkedTraitData, TraitRequirements = TraitRequirements }))
'
```
(run from `fixtures/h2-shape/`; analogous one-file-load for `h1-shape/`).

## Coverage matrix

Numbers match the 15 items from the brief. "H2" = `fixtures/h2-shape`,
"H1" = `fixtures/h1-shape`. Both fixtures independently produce the id(s)
noted; check `expected.json`'s `_covers` annotations on each record for
the exact reasoning.

> **Read this as a map of the inputs, not a claim about the assertions.**
> Each row says the fixture *contains* a shape. Whether the extractor then
> does anything with it is a separate question, and for ten rows the answer
> used to be no — the shape went in and the golden recorded the extractor's
> silence as the expected output. That is what a snapshot does, and it is why
> `golden/` is the assertion while `expected.json` stays the target (above);
> but a reader scanning this table for "what is tested" would be misled, so
> the gaps are named here rather than left to be rediscovered.
>
> **Four of the ten have since closed**, and the goldens were reviewed line by
> line rather than refreshed, because in each case the diff *was* the finding:
>
> - **Row 7 (H2)** — `InfusionRadianceBoon` now emits an `activation`
>   requirement at its higher threshold, distinct from the obtain threshold in
>   `prereq`.
> - **Row 9 (both games)** — the asymmetric negation now lands in `blockedBy`
>   instead of `exclusiveGroup`. `CindraReclaimBoon` and `SableEmberComboTrait`
>   each carry one blocker and no group, which is the shape the row asks for.
> - **Row 11 (H2)** — `CindraMalformedBoon` refuses. Its `prereq` is the
>   `UNCLASSIFIED_NEGATION` marker and the run records a matching build failure,
>   which is the pass condition the "Fields" section below states. It had been
>   failing in a way that section did not enumerate — silent passthrough, exit 0
>   — for as long as the fixture has existed.
> - **Row 15 (both games)** — the dangling reference is now asserted, by a test
>   that runs the validator over the fixture output rather than by the golden.
>   `validate.py` has its own test file for the first time.
>
> **Rows 1, 3, 4, 14 and the `OneOf` half of 2 and 9 have since closed too**,
> and for one cause. `normalize_h1.py` used to walk a written-out map of the ten
> real gods, so the fixture's invented gods matched nothing and the entire
> `LootData` pass produced nothing: `gods.json`, `named_sets.json` and
> `keepsakes.json` were all `{}`, `SablePyreTrait`'s prereq was `null`, and
> `SableEmberComboTrait` kept only its inline `RequiredFalseTrait`. A god's
> table is now recognised by its shape — it inherits `BaseLoot` and either keeps
> the `GodLoot` flag or has a speaker — which is what the fix note here asked
> for, and no real name entered these files to get it. What that turned on:
>
> - **Rows 1, 3 and the `OneOf` half of 2** — the `LinkedUpgrades` prereqs now
>   resolve. `SableEmberComboTrait` carries its `OneOf` (and stands a rung
>   higher for it), `SablePyreTrait` its `OneFromEachSet`.
> - **Row 4** — `SablePyreTrait` is offered by both `SableUpgrade` and
>   `AuricUpgrade` and now comes out as a Duo of the two, which is the only
>   thing a Hades I Duo ever is. It also declares `God = "Sable"`, so it covers
>   the case where the two disagree.
> - **Row 14** — `FennickUpgrade` gained a `Speaker`, without which nothing
>   separates a non-pool god from the hammer. `Fennick` is now `NonPoolSlot`
>   through the `GodLoot = false` resolution the row describes, rather than
>   through its boon's own `God` field.
>
> The rest still stand, verified by running both normalizers and reading
> `golden/`:
>
> - **Row 13 (both games)** — neither normalizer implements `DebugOnly`
>   exclusion at all; the string does not appear in `src/*.py`. Both
>   `SableDebugTrait` and `CindraDebugOnlyBoon` are in their goldens. The
>   fixtures hold the input the rule would need, and the rule is not written.
> - **Row 6's element-affinity half (H2)** — `CindraStrikeBoon` has
>   `elementAffinity: null` in the golden. The affinity resolver matches against
>   a hardcoded table of the real games' element bases, which the fixture's
>   invented `EmberAffinityBase` cannot be in. The rarity and duo/legendary
>   halves of that row *are* exercised.
>
> None of these are fixture defects: the inputs are right and are what a fix
> would be written against. They are places where the golden still freezes an
> omission, so **a change that starts emitting one of these fields will show up
> as a large golden diff and must be reviewed as a correctness change, not
> refreshed mechanically.** The four rows above were closed exactly that way.

**Note on #14 / `godKind` in general:** the two fixtures deliberately test
*two different real signals* for the same `PoolSlot`/`NonPoolSlot`
distinction, matching a genuine structural difference between the games'
data (see `../out/clarifications.md` §2 for the real-data finding this
mirrors): `h2-shape` has no `LootData` file at all, so `Orithia`'s
`NonPoolSlot` status comes purely from the `CameoBoonBase` `InheritFrom`
marker. `h1-shape` *does* have a `LootData.lua`, so `Fennick`'s
`NonPoolSlot` status is tested via a real, resolved `GodLoot = false`
field on `FennickUpgrade` (inherited-through-override from `BaseLoot`'s
`GodLoot = true`) — the mechanism the real games actually use for their
non-pool "gods" (Hermes in both games). Between the two fixtures, both
real-world signals are exercised.

## Fields in `expected.json`

Each boon record: `id, god, duoGods, name, descriptionRef, icon,
boonCategory, godKind, slot, tier, rarity, exclusiveGroup, blockedBy,
elementAffinity, prereq, activation, source`.

- **`name` / `descriptionRef` are always `null`** in both fixtures. Neither
  fixture includes a localized text-bundle input file (the brief's file
  list didn't call for one), so name/description resolution isn't
  exercised here — that logic is covered by the real extraction pipeline
  (`../src/parse_text_bundle.py`) against the real games' `.sjson` files
  instead. Don't read anything into `null` here beyond "not tested by this
  fixture."
- **`tier`** (`Core` | `Legendary` | `Duo` | `Infusion` | `Cameo`) is *not*
  a literal field in either real game's data — it's an interpretive
  summary of which base template a boon's `InheritFrom` chain bottoms out
  at, distinct from `rarity` (the raw `RarityLevels` keys available,
  matching the real extraction's schema). Note Hades I's real quirk,
  reproduced faithfully in `h1-shape`: Duo-shaped boons still get
  `tier: "Legendary"` there (not `"Duo"`), because Hades I's real
  `SynergyTrait` reuses the `Legendary` `RarityLevels` key rather than
  having a separate `Duo` tier — see `raritiesNeverUsedByAnyBoon_notes` in
  `../reference/hades1/validation.json` for the real-data version of this
  finding.
- **`exclusiveGroup`** is populated only for a *symmetric* clique (every
  member lists every other member back) — an array including the boon's
  own id, sorted, identical across every member of the clique.
  **`blockedBy`** is populated only for a *one-directional* negation — an
  array of the id(s) that block this boon, with no claim that those ids
  reciprocate. A boon should never have both populated in these fixtures.
- **`prereq.type: "UNCLASSIFIED_NEGATION"`** (H2 fixture, `CindraMalformedBoon`
  only) is the expected output for coverage #11 — its presence, paired
  with a matching entry in `validation.buildFailures`, IS the pass
  condition. An extractor that instead silently drops this boon, silently
  assigns it a normal `blockedBy`/`exclusiveGroup`, or crashes, should be
  considered failing this fixture. **The current extractor fails it in a
  fifth way this list did not anticipate — silent passthrough with exit 0 —
  and the golden freezes that as the expected output.** See the callout above
  the coverage matrix. Do not refresh that golden mechanically when the
  classifier is fixed: the diff is the point.
- **`prereq.synthesizedSetId`** (H1 fixture, `SablePyreTrait`) is
  illustrative, not a prescribed literal string — what the fixture
  actually checks is *stability*: the same set content must always
  resolve to the same identity, wherever and however many times it
  appears, even though Hades I's data never names it. Match on that
  property, not on the exact string shown.

## Known gap this fixture set intentionally surfaces

`h1-shape/expected.json`'s base-template exclusion rule (a trait counts as
a real boon only if some god's `PriorityUpgrades`/`WeaponUpgrades`/`Traits`
list or `LinkedUpgrades` mentions it) is **more principled than the
one-off script that produced the earlier real Hades I extraction**
(`../src/normalize_h1.py`) — that script had no per-god-file signal to exclude
base templates by (Hades I has no per-god files at all, unlike Hades II,
where "only defined in the base file, never a per-god file" was the
exclusion signal used), and as a result **did not exclude `ShopTier1Trait`
/ `ShopTier3Trait` / `SynergyTraitTemplate` from
`../reference/hades1/boons.json`** — they're in there as ordinary (if
nonsensical) boon records today. If an
extractor built against this fixture is meant to supersede that script,
expect `../reference/hades1/boons.json` to shrink slightly (by however many base
templates Hades I's real `TraitData.lua` contains) once it adopts this
fixture's rule; that's a fix, not a regression.
